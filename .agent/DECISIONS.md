# Decisions

## D1. pnpm workspaces

pnpm is installed and handles workspaces and strict dependency isolation better than npm.

## D2. Merchant portal on Vite, public dashboard on Next.js

The brief's architecture puts the public dashboard on Next.js (SSR for SEO); the merchant portal is a
plain React SPA behind login, so Vite is enough there.

## D3. Local PostgreSQL fallback when Docker is unavailable

Cloud sessions have the Docker CLI but no daemon. Verification uses a local PostgreSQL 16 cluster with the
same credentials as `docker-compose.yml`; Docker files are still written and kept correct.

## D4. Current major versions

Express 5, Zod 4, Drizzle ORM 0.45 / drizzle-kit 0.31, better-auth 1.x, Next.js 16, Vitest for tests.

## D5. Shared package resolution via a `source` export condition

`@classifieds/shared` exports `source`/`types` → `src/index.ts` and `default` → `dist/index.js`. Dev tools
(tsx, Vitest, Vite) resolve the `source` condition so no build is needed during development; production
builds use the compiled `dist`.

## D6. Listing schema — universal core + `attributes` jsonb

Core fields fit any classifieds niche: `title` (≤120), `description`, `price` (integer in minor units,
`null` = price on request), `currency` (ISO code, default `UAH`), `city`, `category_id`, `status`
(`active`/`paused`/`sold`), `seller_id`, timestamps. Niche-specific fields go into `attributes` (jsonb,
default `{}`), validated per category later if needed — new niches need no migrations. If a niche field
must be filtered/sorted heavily, it can be promoted to a real column or get an expression index.
Money as integer minor units avoids floating-point errors. Photos live in `listing_photos` with a
`position` for ordering. Categories are a tree via `parent_id`.

## D7. node-postgres driver

`pg` with `drizzle-orm/node-postgres`: the most common driver, works with better-auth's Drizzle adapter
and drizzle-kit.

## D8. Migrations applied by our own script, generated by drizzle-kit

`db:generate` (drizzle-kit, needs `NODE_OPTIONS=--conditions=source` so it reads the shared package's
sources) writes SQL to `apps/api/drizzle/`. `db:migrate` runs Drizzle's programmatic migrator, which also
works from the compiled `dist/` inside Docker (no drizzle-kit in production). The category seed is
idempotent (upsert by slug) so it is safe to run on every deploy.

## D9. API image built with `pnpm deploy`

The Dockerfile installs only the API's dependency subtree, builds shared + api, then `pnpm deploy --prod
--legacy` produces a self-contained folder (dist, drizzle migrations, prod node_modules with the compiled
shared package). The container runs migrations and the idempotent seed on start, then the server.
Each package declares its own `typescript` devDependency because the filtered install skips the root.

## D10. Auth tables owned by our Drizzle schema

The better-auth core tables (`users`, `sessions`, `accounts`, `verifications`) are written by hand in
`schema.ts` (plural names like the rest, adapter `usePlural: true`) and migrated by drizzle-kit — one
migration tool for the whole DB, no better-auth CLI. User IDs are UUIDs (`generateId: crypto.randomUUID`).
Profile fields `phone`/`city` live on `users` as better-auth `additionalFields` with `input: false`
(changed only via `PATCH /api/me`). Deleting a user cascades to sessions, accounts and listings.
Telemetry is disabled.

## D11. Auth secret

`BETTER_AUTH_SECRET` (≥32 chars) is required when `NODE_ENV=production`; in dev/test a fixed insecure
default is used so the project runs without setup. An empty value in `.env` counts as unset.

## D12. Auth endpoints are better-auth's own

Sign-up / sign-in / sign-out / get-session are better-auth's endpoints under `/api/auth/*`
(`/sign-up/email`, `/sign-in/email`, `/sign-out`, `/get-session`) — no wrapper routes. Its CSRF check
requires an `Origin` from `TRUSTED_ORIGINS` on cookie-authenticated POSTs; non-browser clients (curl,
tests) must send one.

## D13. Profile fields and what is public

`PATCH /api/me` accepts only `name`, `phone`, `city` (strict object, at least one field; empty string
clears `phone`/`city`). Email changes go through better-auth, not this endpoint. The public profile
(`GET /api/users/:id`) shows `id`, `name`, `image`, `phone`, `city`, `createdAt` — the phone is the
seller's contact on a classifieds board and is optional; the email stays private. Services return
plain DTOs with ISO-string dates matching the shared schemas.

## D14. Listing input rules and status transitions

Create: `title` 3–120, `description` ≤5000, `price` integer minor units 0–2e9 or `null` (default),
`currency` 3-letter ISO (upper-cased, default `UAH`), `city`, `categoryId`, `attributes` — a flat map of
identifier keys → string/number/boolean (≤30 keys): flat scalars stay filterable via jsonb operators.
Strict objects: `status`/`sellerId` cannot be set by the client. Update is a partial of the same fields;
status changes have their own endpoint. Transitions: active ↔ paused, active/paused → sold; `sold` is
final (re-selling means a new listing). Setting the current status again is an idempotent no-op. The
transition table lives in `@classifieds/shared` so the merchant portal can show only valid actions.

## D15. Listing visibility, ownership and errors

`active` and `sold` listings are public (a sold item stays viewable, marked sold); `paused` is visible only
to its seller — everyone else gets 404, so its existence is not leaked. Writes by a non-owner get 403
(as the plan requires); unknown or non-UUID IDs get 404. A listing must use an existing leaf category
(400 otherwise). Sold listings are read-only (409 on edit), but can still be deleted. Invalid status
transitions are 409 Conflict (valid input, wrong state). Writes run in a transaction that locks the row
(`SELECT … FOR UPDATE`) so the ownership/state check and the update cannot race.

## D16. Category tree endpoint

`GET /api/categories` returns the whole tree (`{ id, parentId, slug, name, children }`, siblings by
`sort_order`) in one response: it is a few dozen rows, read in one query and assembled in memory, and both
frontends need the full tree for selects and filters. It is public and cacheable for 5 minutes because
categories change only through the seed on deploy.
